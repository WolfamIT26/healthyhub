# Authentication Contract V1 / Contract xác thực V1

## Metadata / Thông tin

- Public contract: `v1` (backward-compatible clarification before implementation).
- Internal revision: `0.2.0`, approved 2026-08-06.
- Email is the only V1 login identifier: trim, Unicode-safe lowercase, maximum 254 characters, globally unique in single-tenant V1.

## Token Delivery / Phân phối token

| Client | Access token | Refresh token |
| --- | --- | --- |
| Web | JSON field `accessToken`; keep in memory only | Cookie `__Host-hh_refresh`; never JSON/localStorage/sessionStorage |
| Future mobile | JSON field `accessToken`; secure OS storage | JSON field `refreshToken` only when request header `X-Client-Type: mobile`; secure OS storage, sent as `X-Refresh-Token` |

Web refresh cookie: opaque random value, `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age` matching refresh lifetime; host-only, no `Domain`. `__Host-` requires `Path=/`. Login/refresh set it; logout clears it with identical attributes and `Max-Age=0`. Responses that deliver/set tokens use `Cache-Control: no-store`.

Web `POST /auth/refresh` requires the cookie plus `X-CSRF-Token`; server validates signed double-submit token and exact `Origin`/trusted `Referer`. CORS with credentials uses an exact environment allowlist, never `*`. Login/register/forgot/reset/verify/resend validate Origin when present and use `application/json`; protected state-changing calls use Bearer and the normal authorization policy.

## Password Contract / Contract mật khẩu

- New password: 12–128 Unicode characters; spaces allowed; no mandatory composition rule.
- Reject a configured local common-password denylist; never call an external breach service synchronously.
- Hash with Argon2id; baseline memory 19 MiB, iterations 2, parallelism 1; benchmark and raise cost per environment without weakening this production baseline. Unique salt is generated by the implementation.
- Current password is required for change. Reset requires a valid one-time token. Reset revokes all sessions; change revokes all other sessions and rotates the current session.
- Password, hash and rejected value are never returned or logged.

## Success Data / Dữ liệu thành công

All payloads are inside the standard success envelope.

| Operation | `data` contract | Cookie behavior |
| --- | --- | --- |
| Register | `{ user: ActorSummary, verification: VerificationSummary }` | none |
| Login | `AuthenticationResult` | web: set refresh; mobile: return refresh in `data` |
| Refresh | `TokenRefreshResult` | web: rotate/set refresh; mobile: return rotated refresh |
| Logout | `{ sessionStatus: "revoked" }` | clear web refresh cookie |
| Session | `CurrentSession` | none |
| Forgot | `{ accepted: true }` with the same message for every syntactically valid email | none |
| Reset | `{ passwordChanged: true, sessionsRevoked: true }` | clear web refresh cookie |
| Change | `{ passwordChanged: true, otherSessionsRevoked: true }` | rotate current web refresh cookie |
| Verify | `{ verificationStatus: "verified" }` | none |
| Resend | `{ accepted: true }` with enumeration-safe message | none |

`AuthenticationResult`: `accessToken`, `tokenType: "Bearer"`, `accessTokenExpiresAt`, `session`, `actor`; optional `refreshToken` and `refreshTokenExpiresAt` are mobile-only. `TokenRefreshResult` has access-token metadata, `session`, and the same mobile-only fields. `CurrentSession` has session ID/status/issued/expires, actor, persisted role codes, effective permission codes and `permissionsVersion`. No password/hash/raw reset or verification token is returned.

## Roles & Permissions / Vai trò và quyền

- Guest is transient and not stored. Persisted V1 roles: `CUSTOMER`, `STAFF`, `MANAGER`, `ADMINISTRATOR`. `SUPER_ADMIN` is a reserved future platform role and is neither seeded nor assignable in V1.
- Registration always assigns `CUSTOMER`. Roles and permissions are many-to-many through User-domain tables; backend authorizes by effective permission.
- Access token contains subject, session ID, role codes and `permissionsVersion`, not the full permission list. Sensitive authorization resolves current effective permissions/account/session state server-side.
- `users:manage` permits Administrator to lock/unlock/disable accounts. Owner may revoke the current session; `sessions:manage` permits Administrator to revoke another user's or all sessions. Every privileged action is audited.

## Canonical Errors / Lỗi chuẩn

| Code | HTTP | Public behavior |
| --- | --- | --- |
| `AUTH.AUTHENTICATION.INVALID_CREDENTIALS` | 401 | Generic login message |
| `BUSINESS.AUTHENTICATION.ACCOUNT_LOCKED` | 423 | May provide safe `retryAfter`, no account discovery in public pre-auth flow |
| `BUSINESS.AUTHENTICATION.ACCOUNT_DISABLED` | 403 | Generic login response pre-auth; explicit only for an already authenticated owner/admin flow |
| `CONFLICT.AUTHENTICATION.EMAIL_ALREADY_EXISTS` | 409 | Register only |
| `AUTH.AUTHENTICATION.TOKEN_INVALID` | 401 | Generic token failure |
| `AUTH.AUTHENTICATION.TOKEN_EXPIRED` | 401 | Token context only |
| `AUTH.AUTHENTICATION.TOKEN_REVOKED` | 401 | Token context only |
| `AUTH.AUTHENTICATION.REFRESH_TOKEN_REUSED` | 401 | Revoke family; generic re-login message |
| `VALIDATION.AUTHENTICATION.PASSWORD_POLICY_FAILED` | 422 | Safe field validation details |
| `AUTH.AUTHENTICATION.RESET_TOKEN_INVALID` | 400 | Combines invalid/expired/used to limit probing |
| `PERMISSION.AUTHENTICATION.DENIED` | 403 | Authenticated actor only |
| `RATE_LIMIT.AUTHENTICATION.EXCEEDED` | 429 | Include `Retry-After` |

Login uses the same public message for nonexistent account, wrong password, disabled, unverified and locked states; internal code/audit may differ. Forgot/resend always use accepted responses for valid input.
